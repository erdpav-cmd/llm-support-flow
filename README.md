# LLM Support Flow — автоматизация обращений «от входа до действия»

Мини-сервис для службы поддержки: принимает текст обращения, структурирует его
LLM в строгий JSON, проверяет качество, эскалирует сомнительные случаи человеку,
создаёт задачу менеджеру и пишет каждый шаг в журнал аудита.

Учебный кейс-практика: автоматизация бизнес-процесса с LLM и контролем качества.

## Проблема → Решение → Результат

- **Проблема.** Входящие обращения разбирает человек: читает, определяет категорию,
  заводит задачу в журнал. Около 6 минут на обращение, ошибки и потерянные лиды.
- **Решение.** Процесс «вход → LLM (строгий JSON) → контроль качества → действие»:
  категория, резюме, приоритет, задача менеджеру, эскалация сомнительных случаев,
  журнал аудита по каждому шагу — даже когда LLM недоступна.
- **Результат.** 50% обращений закрываются без человека, обработка ~2 секунды,
  себестоимость 100 обращений ~4 ₽, каждое решение прослеживается в журнале.

## Архитектура

```text
POST /ingest
  → отсечение пустого входа (0 ₽) и детектор prompt injection
  → LLM gpt-4o-mini, temperature 0.2, строгий JSON
  → валидация по Pydantic-схеме
  → детерминированные правила эскалации (решает код, не модель)
  → ДЕЙСТВИЕ: задача в SQLite (таблица tasks)
  → АУДИТ: журнал audit_log (вход + сырой ответ LLM + результат + статус)
```

## Контроль качества и эскалация

| Правило | Результат |
|---|---|
| Вход короче 3 символов | `invalid_input`, LLM не вызывается (0 ₽) |
| Маркеры prompt injection в тексте | эскалация, `priority=high`, LLM не вызывается |
| LLM недоступна (401 / 429 / таймаут) | `llm_error` + безопасный результат оператору |
| JSON не прошёл схему | `invalid_json` + безопасный результат |
| `confidence = low` | эскалация |
| Нет контакта для ответа | эскалация |
| Категория не определена (`other` + не `high`) | эскалация |

Ключевой принцип: **модель извлекает факты, решение принимает код**.
В тестах модель возвращала разные значения `escalate` на одинаковых по смыслу
входах, а в тесте prompt injection подчинилась инструкции атакующего.
Детерминированные правила удержали процесс в обоих случаях.

## Быстрый старт (5–10 минут)

Требования: Python 3.12+, git.

```bash
git clone https://github.com/erdpav-cmd/llm-support-flow.git
cd llm-support-flow
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
```

Создайте файл `.env` по образцу:

```text
LLM_API_KEY=ваш_ключ_ProxyApi
LLM_BASE_URL=https://api.proxyapi.ru/openai/v1
LLM_MODEL=gpt-4o-mini
LLM_TEMPERATURE=0.2
RATE_LIMIT_PER_MINUTE=5
DB_PATH=data/app.db
```

Запуск:

```bash
uvicorn app.main:app --reload --reload-dir app --port 8000
```

Документация Swagger: http://127.0.0.1:8000/docs
Проверка подключения к LLM: `python check_sdk.py`

## Как подать вход

`POST /ingest`, тело запроса:

```json
{
  "text": "Заказ 1042 не приходит неделю. Я Иван, +79001234567. Верните деньги.",
  "source": "api"
}
```

Пример из PowerShell (кириллица через UTF-8 байты):

```powershell
$body = @{ text = "Заказ 1042 не приходит неделю. Я Иван, +79001234567." } | ConvertTo-Json
$bytes = [System.Text.Encoding]::UTF8.GetBytes($body)
Invoke-RestMethod -Uri http://127.0.0.1:8000/ingest -Method Post -Body $bytes -ContentType "application/json"
```

## Где смотреть результат

- `GET /tasks` — задачи менеджеру и оператору (действие процесса)
- `GET /audit` — журнал: вход, сырой ответ LLM, итог, статус, ошибка, задержка
- `GET /health` — состояние сервиса и счётчики
- `data/app.db` — SQLite, таблицы `tasks` и `audit_log`

## Мини-экономика

- Вручную: ~6 минут на обращение → 100 обращений = 10 часов работы оператора.
- После автоматизации: triage мгновенный, менеджер проверяет готовую задачу
  (~0,5 мин) → 100 обращений = ~50 минут.
- Экономия: ~9 часов на 100 обращений. При ставке 400 ₽/час это ~3600 ₽
  против ~4 ₽ расходов на LLM.
